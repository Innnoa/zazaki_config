# AGENTS.md — Codex 工作规则（{{HOME}}）

最后更新：2026-04-08  
适用目录：`{{HOME}}`

本文件只保留当前环境下需要长期携带的核心规则。当前目录以 `vibe` 为主工作流，不再把 `SESSION_MODE=full`、`AGTX_CONTEXT` 和 `RUNBOOK_FULL.md` 当作活跃执行入口。

## 1. 规则优先级

- 更近层级的 `AGENTS.md` 优先。
- 其次遵循本文件。
- 再其次遵循项目文档与 Codex 默认行为。
- 任何本地规则都不能绕过安全边界、审批策略或沙箱限制。

## 2. 核心原则

- 结论必须基于代码、配置、命令结果或文档证据，禁止凭空假设。
- 优先复用标准生态、官方 SDK 和项目既有实现。
- 优先修复缺陷，再做新增能力。
- 默认自主推进；只有缺少关键事实或涉及高风险操作时才询问用户。
- 不得虚构工具、MCP、文件、外部状态或命令结果。
- 不得把 `~/.codex/` 当成普通项目产物目录滥用。
- 不得让规则文档与当前真实配置漂移；规则以当前环境和已验证配置为准。

### 2.1 交流与输出约定

- 默认使用简短、自然、直接可读的中文；少写底层细节、黑话和空话。
- 非中文内容统一写成 `英文内容`（中文解释），放在同一行。
- 文件路径写成正常文本，不做可点击链接；引用依据时尽量直接写原文。
- 默认一次性完成当前任务后再汇报；只有关键不确定时先问清楚。
- 默认先给一句结论，再补最多 3 个短点；只回答当前问题，不主动扩展。除非用户明确说“展开”，否则不要写成长篇方案树。
- 例子只给 1 个最小例子；回答超过 150 字时先压缩；用户说“一个一个来”时，每次只讨论一个决策点。
- 文风保持温和、自然、像协作说明；少用命令式、审查式、AI 套话和拟物化表达，优先使用“读取、整理、生成、更新、保存”等朴素词。
- 写 README、说明文档、汇报文档时，先参考同目录已有文档的语气，尽量贴近原有写法。

## 3. 默认工具与运行偏好

- 本地检索：优先 `rg`、`find`、`git grep`。
- 文件修改：优先 `apply_patch`。
- 多步骤进度：使用 `update_plan`。
- 复杂推理：优先 `sequential-thinking`；需要任务拆解时优先 `shrimp-task-manager`；不可用时降级到显式本地推理或 `update_plan`。
- 官方文档：优先 `context7`。
- 外部检索：优先 `exa_search`，原生 `web` 仅在可用时补充使用。
- 本地代码语义检索：优先 `serena`。
- 当前 host 的稳定 MCP 集合以 `config.toml` 为准；截至本次收口，默认集合是 `context7`、`exa_search`、`serena`、`sequential-thinking`、`shrimp-task-manager`。
- 并行独立子任务：仅在用户明确要求多代理、委派或并行处理时使用 `spawn_agent`。

### 3.1 Vibe-First 约定

- 当前默认长流程入口是 `$vibe`。
- 满足以下任一条件时，优先按 `$vibe` 受控流程推进：
  - 用户显式提到 `$vibe`、`/vibe` 或 `vibe`
  - 任务涉及多文件修改、跨轮跟踪、冻结需求/计划、较强验证或阶段清理
  - 任务不是“单点小改”或“简短问答”
- 单文件轻改、短问答、一次性排查可直接走轻量路径，不强制完整 `vibe` 产物。
- `$vibe` 的默认阶段为：`skeleton_check`、`deep_interview`、`requirement_doc`、`xl_plan`、`plan_execute`、`phase_cleanup`。
- `vibe` 产物默认写入：
  - `docs/requirements/`
  - `docs/plans/`
  - `outputs/runtime/vibe-sessions/<run-id>/`
- 当前环境默认由主代理单线执行；即使在 `vibe` 路径下，没有用户明确授权也不要自行展开多代理。

### 3.2 Superpowers 接入约定

- 若 `~/.agents/skills/superpowers/` 存在，且当前会话已在安装或更新后重启，则视为 `obra/superpowers` skills 可用。
- 优先级保持为：用户直接指令 / 更近层级 `AGENTS.md` / 本文件明确约束 > `vibe` 与其他 skills > Codex 默认行为。
- skills 只可在不违反本文件、安全边界、审批策略、沙箱限制和项目本地规则时使用。
- `brainstorming`、`writing-plans`、`executing-plans` 可作为 `$vibe` 的辅助流程，但不得重新引入第二套需求面、计划面或运行时权威。

### 3.3 删除操作约定

- 删除文件只能使用 `trash`，不得默认使用 `rm`。
- 若环境未安装 `trash`，或场景不适合使用 `trash`，必须先向用户说明并确认。

## 4. 执行路径

- 默认存在两条路径：
  - `quick`：轻量路径，适用于单点问题、简短问答、轻量脚本或单文件修改
  - `$vibe`：受控路径，适用于多步骤、强验证、跨轮或用户显式要求的任务
- 当前目录不再维护 `SESSION_MODE=full` 和 `AGTX_CONTEXT` 作为活跃模式。
- 旧文档若仍提到 `SESSION_MODE=full`、`AGTX_CONTEXT` 或 `RUNBOOK_FULL.md`，视为历史兼容信息，不再作为新任务入口。

## 5. Quick 路径

- 先做最小必要扫描，再直接回答或动手。
- 只有在任务依赖历史上下文、涉及多文件修改、需要跨轮跟踪时，才读取并回写 `AI_GUIDE.md`。
- 简单任务不强制使用 `sequential-thinking`、`shrimp-task-manager` 或完整治理产物。
- 仍需说明实际验证情况和残留风险。

## 6. $vibe 受控路径

- 任务进入 `$vibe` 后，默认先固定目标、交付物、约束、验收标准和非目标，再冻结到需求文档。
- 需求文档是后续执行的单一事实来源，不应继续依赖整段聊天历史。
- 计划文档必须覆盖内部执行等级、阶段顺序、文件范围、验证命令、回滚方式和清理要求。
- 执行阶段可以调用受限辅助 skill 或工具，但不得创建第二份正式 requirement 或第二份正式 plan。
- 完成前必须留下验证证据与清理回执，不能只口头宣称完成。
- 若任务本身很小，但用户显式使用 `$vibe`，仍应至少补齐最小 requirement、plan 和 cleanup 记录。

## 7. AI_GUIDE 最小约束

- `AI_GUIDE.md` 用于保存项目级 AI 审计与跨轮上下文，不得记录密码、令牌、密钥等敏感信息。
- `quick` 路径下，仅在需要跨轮连续性或发生实质性文件改动时维护。
- `$vibe` 路径下，默认读取概要区与最新锚点后的增量内容，并在结束前追加精简记录与新锚点。
- 不得无故覆盖、伪造或清空关键审计记录。

### 7.1 上下文外部化

- 稳定事实应外部化为独立文件，不依赖聊天历史作为唯一来源。
- 长期规则、当前任务状态、技术决策和一次性交接应分层保存，同类状态只保留一个权威来源。

### 7.2 状态文件职责

- `AI_GUIDE.md`：项目级审计、跨轮摘要、关键验证结论、最新读取锚点。
- `CURRENT_TASK.md`：当前任务的目标、范围、验收标准、相关文件、当前状态、下一步。
- `DECISIONS.md`：重要技术决策的结论、原因、影响范围。
- `handoff/`：会话切换时的一次性交接摘要。
- `docs/requirements/`：`$vibe` 冻结后的需求文档。
- `docs/plans/`：`$vibe` 冻结后的执行计划。
- `outputs/runtime/vibe-sessions/`：`$vibe` 的阶段回执、清理结果与运行留痕。

### 7.3 默认读取与回写策略

- 新会话不得把前文聊天记录当成唯一上下文来源，应优先读取最小必要的状态文件。
- 默认读取顺序为：`AGENTS.md` → `CURRENT_TASK.md` → 必要的 `DECISIONS.md` 条目 → 必要代码与配置 → `AI_GUIDE.md` 概要区和最新锚点后的增量内容。
- 若任务延续已有 `$vibe` run，还应补读最近的 requirement、plan 和对应 runtime receipt。
- 任务目标、范围、验收标准或下一步变化时，应更新 `CURRENT_TASK.md`。
- 出现可复用的重要取舍时，应更新 `DECISIONS.md`。
- 会话切换时应生成 10 到 20 行的精简 `handoff`，不要保存整段聊天、整份 diff、重复日志或过时猜测。

## 8. 需要确认的事项

- 删除核心配置文件
- 破坏性数据或 schema 变更
- `git push`、远端合并、远端发布
- 越过当前沙箱或权限边界的命令
- 连续三次同类失败后仍要尝试新策略
- 清空、重写或迁移既有 `AI_GUIDE.md` 历史内容

## 9. 交付要求

- 说明改了什么。
- 说明为什么这样改。
- 说明实际执行了哪些验证。
- 说明残留风险、未覆盖项或无法完成的部分。
- 若任务走了 `$vibe` 路径，还应说明 requirement、plan 和 runtime receipt 的落点。
