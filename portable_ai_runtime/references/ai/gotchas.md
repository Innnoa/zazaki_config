## AI 坑点

只记录同时满足以下至少两条的坑点：

- 大概率会再次出现
- 漏掉后会明显浪费时间、质量或验证成本
- 单看代码本身不容易直接看出来

边界：gotchas 记录系统运行时的实际行为坑点（"踩到就会出问题"）。
anti-patterns 记录 Agent 行为层面的错误模式（"不该这样做"）。
两者有交叉时，以 anti-patterns.md 为主落点，本文件只保留纯系统行为类坑点。

## 系统行为坑点

- Context 压缩后如果只剩顶层摘要而没有显式路由表，任务容易错误继承上一轮路径；这类问题应优先通过路由文件和薄壳入口解决，而不是靠记忆补救。
- `opencode.json` 这类配置只要漏掉 `rules/ai/*.md` 的注入，规则即使写对了也可能不会自然进入上下文。
- 长会话新任务如果不重读入口，特别容易错误继承上一轮的路由、验证或完成口径。
- 治理文件删除/合并时，不仅要检查 `.md` 文件的交叉引用，还要 grep 脚本（`.sh`/`.py`）和数据文件（`.tsv`/`.json`）中的硬引用，否则验证脚本可能静默失败。
- `.doc` 旧格式（OLE Compound Document）不能用 Read 工具直接读取文本内容，需用 olefile + python-venv 先提取文本流。
- 跨目录引用在 markdown 反引号中必须写完整相对路径（如 `workflows/ai/fix-and-review.md`），不要省略目录前缀，否则交叉引用扫描脚本会误报 broken ref。
- `npx tsc` 在未安装 typescript 的目录会命中 npm 的 tsc 占位包（"This is not the tsc command you are looking for"），必须用 `npx -p typescript tsc`；独立编译缺 `@types/node` 时报 TS2591，语法级校验可用 `--noCheck`（与 opencode esbuild 加载方式等价），全类型校验需装 `@types/node`。
- opencode 新版本 tsc 报 `Option 'moduleResolution=node10' has been removed` 时，改用 `--moduleResolution node16` 或 `bundler`。
- `mcp-server-fetch`（uvx 方式）与 `mcp` SDK ≥2.0.0 不兼容：SDK 2.0 把 `McpError` 改名为 `MCPError`，旧包导入 `from mcp.shared.exceptions import McpError` 启动即崩，MCP client 表现为 `-32000: Connection closed`。修复：`uvx --from mcp-server-fetch --with "mcp<2.0.0" mcp-server-fetch`（临时 venv 或固定版本同样可行）；排查时先手动 spawn 该命令看 traceback，不要只盯 client 侧报错。
- (2026-07-31 cpp-project-stability-check) 网络受限环境下验证 FetchContent 依赖项目（re2/Catch2/googletest/pybind11）：复用已有 `build/_deps` 缓存的源码目录可离线重新 configure+build；若目标 build 目录无缓存，可从同仓库其他 worktree/build 的 _deps 复制 `<name>-src` 并加 `-DFETCHCONTENT_FULLY_DISCONNECTED=ON` 跳过下载。
- (2026-08-04 deployment-arm64-fixes) Ansible 离线部署里"离线 copy 任务"会无条件覆盖前面在线下载的正确二进制（install-docker 的 `Install docker-compose` 从 `/data/images/docker-compose-linux-x86_64` 覆盖 `/usr/local/bin/docker-compose`），这是 ARM64 拿到 x86_64 二进制的真实根因；只改下载 URL 不生效，必须给离线 copy 加 `when: host_arch.stdout == 'x86_64'`。
- (2026-08-04 deployment-arm64-fixes) 改 `docker run` 引用的镜像名之前必须核对离线 tar 的 manifest.json RepoTags：portainer_amd64.tar 里是 `portainer/portainer:latest` 而非 `portainer/portainer-ce:latest`；照搬"用 portainer-ce:latest"的 set_fact 会让离线 x86_64 部署因拉取失败挂掉。用 `tar -xOf <image>.tar manifest.json` 查 RepoTags。
- (2026-08-05 opengauss-entrypoint-forkbomb) openGauss CM entrypoint 链会再次调用 generatexml.py；wrapper 若把 generatexml.py 包一层 subprocess 调 generatexml_orig.py，而 CM 脚本又调 generatexml.py，就形成 generatexml_orig.py → generatexml.py → generatexml_orig.py 递归 fork bomb（实测 200+ 进程打死 gaussdb）。修复：generatexml.py 换成纯 no-op 只打印并退出 0，绝不 subprocess 调 _orig。任何"wrapper 调 original"的替换方案都要先排查被替换脚本是否会被其他入口再次触发。
- (2026-08-05 opengauss-su-env-reset) `su - omm -c "gsql ..."` 是登录式 su，会重置 PATH/GAUSSHOME/LD_LIBRARY_PATH，export 放在 `docker exec bash -c` 外层（su 之前）完全不生效（实测仍报 gsql: command not found）。修复必须把 export 放进 su -c 的双引号字符串内、命令之前，并用 `\$PATH` 让 su 登录 shell 展开 omm 自己的 PATH。
- (2026-08-05 async-pull-pattern) 同步任务转 async 模式（docker pull + async_status 拆成两任务）时，若原任务带 `tags`，async 启动任务和 async_status 等待任务必须带相同 tags；只把 tags 留给等待任务会导致 `--tags X` 只跑等待任务、jid 未定义直接 FAIL。
- (2026-08-05 image-pull-skip-check) 给 docker pull 任务加"镜像已加载则跳过"门控（前置 `docker image inspect` + `when: xxx_img_check is failed`）时，检查任务必须与 pull/wait 任务带相同 tags；否则 `--tags X` 运行会跳过检查任务，pull 任务的 `when` 引用未定义变量直接报错。同类门控在新角色里复制时必须把 tags 三处对齐。
- (2026-08-10 opencode-gpt-5.6-sol-migration) `OPENCODE_CONFIG=<template>` 会与常规全局配置面叠加，不能证明模板可独立加载；验证 standalone OpenCode 模板时应使用隔离的 `XDG_CONFIG_HOME`。schema 会拒绝 `_comment` 自定义键，JSONC 说明应使用真正的行注释。
- (2026-08-12 og-cm-migration-p0) openGauss 容器内执行 gs_ctl/gsql 的规范三层引号模式必须带 `LD_LIBRARY_PATH=/opengauss/cluster/app/lib:/opengauss/cluster/tool/lib:/usr/lib64`，否则报 libgssapi_krb5_gauss.so.2 缺失（连 gs_ctl query 都会挂）。目标主机只有 standalone `docker-compose` v2.29.1（/usr/local/bin/docker-compose），没有 docker compose v2 插件，playbook/脚本里用 docker-compose。
- (2026-08-12 keepalived MySQL VIP 部署) keepalived 2.2.8 的 `-t` 语法检查在配置含 vrrp_script 且未启用 script_security 时固定返回 exit 6（SECURITY VIOLATION），原配置也一样；验证应改用 systemctl reload + 观察 VIP/state 日志，不能把 -t 当通过门禁。另：BACKUP 节点 reload 后启动瞬间会短暂进入 MASTER 并绑 VIP，收到高优先级 advert 后自动降级，属正常瞬态。
- (2026-08-12 kafka-rf-fix4) Kafka `kafka-reassign-partitions.sh --generate --topics-to-move-json-file` 从不提升复制因子（只对现有副本做再均衡），RF=1 的 topic 生成的 proposed 计划仍是 1 副本——提升 RF 必须手工构造 reassignment JSON（每个 partition 列 3 个 broker）再 `--execute`。且手工 JSON 的 log_dirs 数组长度必须等于 replicas 数组长度（3 副本必须 ["any","any","any"]），否则 execute 报 "Size of replicas list ... is different from size of log dirs list"。
- (2026-08-12 cft-network-recovery) VM 重启后 docker 自定义外部网络 cft 丢失（只剩 bridge/host/none），引用旧网络 ID 的容器全部 Exited(255)（network not found），restart=always 和普通 `docker-compose up -d` 都无法自愈（compose 判定配置未变、复用旧容器）；修复必须 `docker-compose up -d --force-recreate`。恢复 SOP：① `docker network create cft`（默认 subnet，compose 无固定 IP 故安全）② 按依赖序逐服务 `up -d --force-recreate` ③ 全量健康检查。另：apache/kafka:3.9.0 的 kafka-topics.sh 不在 PATH，需全路径 /opt/kafka/bin/。
- (2026-08-13 deployment-repo-alignment-fixes) Jinja2 模板渲染 bash 脚本时，bash 数组长度语法 `${#hostarr[@]}` 会被 Jinja 解析成注释标签 `{#` → 报 "Missing end of comment tag"（ansible-playbook --syntax-check 不报、渲染时才炸）。修复：正则替换为 `{{ '${#' }}hostarr[@]}` 让 Jinja 原样输出 `${#...}`。验证模板正确性必须用 `docker exec ansible python3` 实际 render（.j2 未渲染时 YAML 校验会误报 `- {{ var }}` 列表项，属正常）。
- (2026-08-13 og-cm-role-deploy-fix) openGauss 企业包三个内层 tarball 的顶层路径前缀不对称：DB tarball 条目带 `./` 前缀（`./bin/gs_ctl`），CM tarball 条目不带前缀（`bin/cm_ctl`）——对三个 tarball 统一用 `--strip-components=1` 会把 CM tarball 的 `bin/` 目录名剥掉，cm_ctl/cm_agent/cm_server 落到 `app/` 根而非 `app/bin/`，PATH 与 `share/config` 路径全部失配（cm_ctl: command not found + cp cannot stat）。正确做法是统一不 strip（`./` 前缀被 tar 自动忽略）。验证：`tar tjf/tzf <tarball> | sed 's|/.*||' | sort -u` 看顶层前缀，strip 前必须先确认所有 tarball 前缀一致。
- (2026-08-13 og-cm-role-split-init-bringup) 多节点 CM/分布式集群的 playbook 结构必须把「每节点初始化」与「集群拉起」拆成两个 play：初始化可以 serial:1（节点本地操作，逐节点安全），但拉起必须并行（所有节点同时启动 om_monitor/cm_agent/cm_server 才能形成 quorum）。若混在同一个 serial:1 play 里，先完成节点会在后续节点未初始化时无限等待 quorum（本例 s001 死等 36×10s×3 轮）。拉起的幂等守卫不能用「进程已存在就跳过」——孤立启动的 om_monitor 处于无 quorum 状态，必须 pkill 陈旧 CM 进程（om_monitor/cm_agent/cm_server）后统一重启才能加入集群。
- (2026-08-13 og-cm-election-stall-deepdive) CM 端口改动必须整段核对 20000-20002（cm_server/DCC/cm_agent 心跳）：曾只放行 20000/tcp，遗漏 DCC(20001)/cm_agent(20002) → 三节点 DCC 无法跨节点通信、选举卡死（每个 DCF 节点只投自己票 vote_count=1、term 卡在 1、cm_server 全 Standby）。恢复验证：放行后 30s 内 cm_002 当选 cm_server Primary，CM 自动 rebuild 备机（Need repair → Building → Normal），cluster_state 自愈到 Normal 1P2S，无需重启容器或清 DCC 数据。写角色时须回查 DECISIONS/AAR 的端口段记录。
- (2026-08-13 keepalived-gauss-vip-failover) VIP 不跟随 CM Primary 的根因：VI 复用了 is_master/priority（如 80/90/100 静态），静态 MASTER 节点非主时 chk 失败 weight -10 与对端静态优先级打平，VRRP 同优先级不抢占 → VIP 滞留非主节点；且"静态 MASTER + 权重"方案无法覆盖任意节点为主的情形。正确设计：三节点同 base priority 100 + 全 BACKUP + chk_gauss_alive weight -50 → 主节点保持 100、非主掉到 50，任意主节点都必赢；保留抢占（nopreempt 会让主变化时 VIP 不跟随）。
- (2026-08-13 nacos-storage-init-fix) 全新 openGauss + Nacos 部署的存储初始化完整链路（三缺一必 crash-loop）：① 建 nacos 用户 + nacos_ms B 兼容库（DDL 只能在本机即 Primary 节点执行——Standby 只读、omm 初识用户禁远程，故必须 `docker exec opengauss-cm su - omm -c` 本地 trust）；② GAUSSDB_SERVICE_HOST 必须指 VIP 而非固定节点 IP（可能指向只读 Standby）；③ schema 不会自动建——Nacos 镜像（prometheus-gaussdb-v2.4.3）内置插件 jar 里有 schema/nacos-openguass-compatible-mysql.sql（12 表），必须显式执行，否则报误导性的 `No DataSource set`（HikariPool 探测成功但 JdbcTemplate 空）。授权必须 `GRANT ALL ON SCHEMA public TO nacos` + `ALTER SCHEMA public OWNER TO nacos`（否则远程建表 permission denied）；gsql 内层 SQL 单引号经多层 shell（ssh→su→gsql）会被吞导致幂等判断失效，可靠做法是把脚本拷入容器 `su - omm -c "bash /tmp/script.sh"` 单层引号执行。

- (2026-08-13 nacos-schema-pw-mismatch) openGauss gsql 不读 PGPASSWORD 环境变量（会交互式提示密码），必须用 `-W "pass"` 传密码——用 PGPASSWORD 写的登录探针/schema 应用会静默失败且无法区分"密码错"与"环境变量不被读"；三重静默（PGPASSWORD + `>/dev/null 2>&1` + 无条件 echo SCHEMA_APPLIED）会掩盖密码不匹配。另：openGauss `password_reuse_time=60`（默认）禁止 60 天内重设相同密码，重置到历史密码必须先 `ALTER SYSTEM SET password_reuse_time=0` + pg_reload_conf，设完再恢复 60。修复要点：登录/查询/schema 应用一律 `-W`；schema 应用不吞错误（失败 exit 1）；幂等用"nacos 用户能真实 SELECT config_info"的 canary（表存在 ≠ nacos 可查，owner=omm 或密码错都会被 canary 拦下）。
