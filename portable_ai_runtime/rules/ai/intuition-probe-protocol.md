## 直觉探测协议

### 作用

让 LLM 在被测物的真实表面可见之前先盲猜其 API/配置/CLI/UI 形状。猜测不是需要评分的错误，而是设计提案；猜测与真实接口的偏差处，默认策略是将接口对齐到猜测——因为猜测代表开发者直觉，而直觉驱动采用。

### 核心原则

**"猜到的就是对的"：** 让 API 变成 LLM 猜测的那样。你只能听到那些硬着头皮克服不熟悉设计的那一小撮用户的反馈，但 LLM 可以低成本、大批量地展示人们默认会伸手的方向。

检验：盲测提示词冻结之后，我有没有不小心把真实接口信息泄露进去？答案键是否从未进入过盲测提示词？

### 触发条件

- 用户说 "is this intuitive"、"would a developer guess this"、"intuition probe"、"blind-test this API/config/CLI"、"test the DX/UX"、"直觉探测"、"盲测这个API"
- 设计阶段已产生具体接口（API 签名、配置格式、CLI 参数、UI 组件），需要验证是否贴合开发者直觉
- grill-me 锁定设计决策后，需要验证决策是否和用户默认期望一致

### 诚实边界

- **N=1 给出的是候选，不是确认：** 单一 LLM 的确信猜测是值得对齐的候选形状，但不能证明它就是大众默认
- **N>1 多代理收敛才能确认：** 至少 2 个独立代理在同一决策点上猜测一致，才标记为高优先级
- **猜对了不等于设计好：** 单一匹配不能证明当前接口具直觉性，可能只是运气

### 流程

1. **收集输入** — 被测物（文件路径/包名/CLI 命令/URL）、粗略目标、可选阅读材料、N（默认 1）
2. **净化目标** — 将粗略目标改写为纯结果描述，剥离所有泄露的标识符（方法名、配置键、flag 名等）。与用户确认
3. **冻结盲测提示词** — 将净化目标填入 `references/intuition-probe/blind-agent-prompt.md` 模板，冻结。冻结后才接触被测物，防止真实表面信息泄露回提示词
4. **读取答案键** — 读被测物的真实表面（源码/签名/schema/--help/组件路由），对外保密
5. **运行盲测代理** — 派发 N 个代理，各持冻结提示词。收集每个代理的 `decision_points` JSON
6. **评分** — 对照答案键，用 `references/intuition-probe/scorer-rubric.md` 分类每个猜测。产出 `findings` JSON，包含代理伸手方向的热悉锚点和对齐建议
7. **（N>1）聚类交叉验证** — 跨代理按决策点分组，标记至少 2 代理一致的为高优先级
8. **报告** — 按 `references/intuition-probe/report-format.md` 输出。N=1 时附加候选声明，不声称设计已被确认

### 核心度量

- **伸手形状：** 代理尝试了哪种形状（方法名、参数顺序、配置结构的命名惯例等）
- **确定度：** 代理记录的置信水平
- **热悉锚点：** 猜测背后的先验来源（其他语言/框架/工具的惯用形态）
- **对齐建议：** 具体怎么改才能对齐猜测
- **（N>1）收敛度：** 多代理在同一决策点上的一致程度

### 与其他流程的接口

- **brainstorming → intuition-probe** — 设计收敛到具体接口后，盲测验证直觉性
- **writing-plans → intuition-probe** — 文件结构、接口边界在敲定前可盲测
- **grill-me ↔ intuition-probe** — grill-me 锁定设计者决策，intuition-probe 验证用户期望。偏差处优先对齐到 LLM 猜测
- **skill 入口** — `skills/intuition-probe/SKILL.md` 作为用户直接入口

### 禁止事项

- 不得在冻结提示词之前读取被测物
- 不得在报告阶段仅凭 N=1 声称"已确认"
- 不得向被测仓库写入任何文件
- 不得将净化步骤中剥离的标识符泄露回代理提示词

### 检验句

问自己：`盲测提示词冻结之后，我有没有不小心把真实接口信息泄露进去？答案键是否从未进入过盲测提示词？`
