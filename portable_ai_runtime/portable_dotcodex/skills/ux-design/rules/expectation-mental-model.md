# 期望与心智模型层

## Jakob's Law（雅各布定律）

用户大部分时间花在别人网站上，所以期望你的和别人的一样运作。不要重新发明轮子。

检验：Logo 在左上角且点它回首页？搜索框看起来像搜索框？关键交互与同平台 App 一致？

- 不要改变用户已有肌肉记忆的交互模式
- Logo 左上角、搜索是放大镜、链接有颜色/下划线、购物车在右上角
- 想创新？先保持结构不变，在细节处做微创新，充分测试再推广
- 反例：Snapchat 2018 重设计；Windows 8 取消开始菜单
- 与 Mental Model 互补：Jakob 说外部期望（来自其他产品），Mental Model 说内部理解（对这个产品）

## Tesler's Law（复杂度守恒定律）

每个系统有固有的不可消减的复杂度。复杂度不会消失，只会转移。

检验：哪些步骤系统可以代劳？表单是否要求用户输入系统本可以推导的信息？复杂度是在帮用户还是给开发省事？

- 好的 UX = 团队吃掉复杂度，把简单留给用户
- 搜索：模糊匹配 + 自动纠错 > 要求精确输入（系统消化了复杂度）
- 地址输入：一个框自动补全 > 省/市/区/街道分 5 个框
- 有些复杂度是价值来源（摄影专业模式、投资风险评估），不能删除
- 决策框架："这个复杂度在帮用户完成任务，还是只在帮系统省事？"

## Aesthetic-Usability Effect（美学可用性效应）

用户倾向于认为好看的设计更好用——即使功能完全相同。颜值即信任。

检验：首屏的视觉设计是否"让人想继续看"？字体层级、间距、色彩是否一致？

- 好看的产品容错率更高：加载慢 2 秒 → "做得挺精致的" vs "太垃圾了"
- 用户链条：看到 → 觉得好看 → 愿意尝试 → 发现好用 → 持续使用
- 基础要素：字号层级清晰、8px 网格间距、主色 1+辅助色 2-3、图标风格统一
- 好看是加速器不是替代品：好看+难用最终也会被抛弃，只是晚一点

## Mental Model（心智模型）

用户脑子里有一套"这东西应该这样用的"预设。界面要么符合它，要么花巨大成本纠正它。

检验：新功能的交互是否借用了已有心智模型？设计是否暴露了底层实现细节？用户能否准确预测每个操作的结果？

- 好的 UX：让表现模型尽可能接近用户的心智模型
- 差的 UX：把实现模型直接暴露给用户
- 利用已有：文件夹=装文件、回收站=删除可恢复、购物车=暂存、开关往右=开
- 引入新模式时需要：首次引导（≤3 步）、空状态教学、渐进式学习
- 发现心智模型：用户访谈、可用性测试、卡片分类

## Postel's Law（波斯特尔定律/稳健性原则）

对输入宽容，对输出严谨。用户打错了、少打了、格式不对了——系统能处理就别报错。

检验：输入框是否接受多种合理格式？搜索是否支持模糊匹配？错误提示是否说了"怎么办"而不只是"出错了"？

- 手机号接受：13812345678、138-1234-5678、(138)1234-5678
- 搜索"ipone"→"你是不是想搜 iPhone？"
- 输出清晰一致：金额始终显示货币符号+两位小数；状态变化给明确反馈（"已保存"+绿色勾）
- 当必须精确（如身份证号）：实时校验 + 解释为什么 + 提供格式提示
- 原理来自 RFC 793 TCP 规范（Jon Postel）
